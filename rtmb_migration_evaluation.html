Bottom Line

With the added program context, the strongest recommendation is not “convert Julia to RTMB.” It is “use this repository to understand and isolate the uncertainty logic, then move survey-result computation into Macebase Analysis so the organization maintains one code base.”

The Julia core is still a stochastic bootstrap engine rather than a differentiable likelihood model, so the technical RTMB conclusion does not change. What does change is the practical recommendation: the first-order problem is point-estimate disagreement with standard survey results, not lack of an RTMB implementation.

Primary goal Reconcile point estimates with standard survey outputs.
Preferred endpoint One maintained code base centered on Macebase Analysis.
RTMB role Optional later, and only if a new model-based spatial estimator is desired.
Critical point: if the organization only wants one code base to maintain, a standalone RTMB reimplementation of Sam’s pipeline is strategically weaker than integrating the uncertainty process around Macebase Analysis.

Program Context

The new context changes the evaluation in an important way. The project is no longer simply choosing a technical language target. It is balancing four practical constraints:

  • the paper is nearly complete, so large methodological rewrites are poorly timed,
  • continued dependence on Sam’s direct implementation work is not a sustainable staffing model,
  • Wavefront Ecology is not currently available as a formal development path,
  • the organization wants one code base to maintain, centered on standard survey operations.

Given those constraints, the natural target architecture is not “replace Julia with another separate uncertainty code base.” It is “reuse the uncertainty-generation ideas, but run standard survey computations through Macebase Analysis inside each simulation replicate.”

Implication: the migration decision should be driven by operational convergence and point-estimate parity, not by language preference alone.

Current Architecture

The repository is organized around a Julia package in src/, survey-specific Julia analysis scripts in analyses/, survey CSV inputs in surveydata/, and a partial R translation in R/. The README explicitly describes the project as Julia-based.

The main replicate loop is implemented in src/ATBootstrap.jl. A single bootstrap iteration:

  1. resamples scaling data,
  2. samples selectivity, age-length, TS, calibration, near-bottom, and trawl assignment effects,
  3. simulates NASC spatially,
  4. converts simulated backscatter into abundance and biomass summaries.

src/preprocess_survey_data.jl Data cleanup, projection, survey grid creation, merge of MACE and GAP inputs Portable to plain R
src/spatial.jl Variogram fitting, LU conditional simulation, z-distribution selection Needs redesign for RTMB

Why RTMB Is Not a Direct Port

RTMB is built for objective functions and automatic differentiation. This repository’s Julia core does not define an objective function to optimize. It defines a simulation engine.

The bootstrap logic in src/ATBootstrap.jl depends on random draws at multiple steps. Those steps include:

  • selectivity parameter draws,
  • age assignment draws from empirical categorical distributions,
  • target-strength perturbations,
  • calibration error draws,
  • near-bottom coefficient draws,
  • stochastic trawl assignment,
  • conditional spatial simulation of NASC.

That is valid for Monte Carlo uncertainty propagation, but it does not map directly to the RTMB workflow. To use RTMB well, the model would need to be reformulated as something like:

  • a latent spatial random field,
  • an observation model for NASC,
  • possibly explicit fixed and random effects for calibration or selectivity,
  • a joint negative log-likelihood that RTMB can evaluate and optimize.

Point Estimate Disagreement

The new context identifies the most important current risk: the uncertainty workflow is producing point estimates that disagree with the standard survey results, even though point estimates were expected to align.

That shifts the near-term priority from uncertainty-method implementation to computational reconciliation. Based on the repository structure, that concern is plausible. The Julia analysis scripts contain their own survey setup, filtering, domain construction, class handling, and replicate-to-summary pipeline rather than delegating the final survey calculation to a shared standard code base.

This means there are several likely sources of point-estimate drift:

  • differences in survey domain construction and grid definition,
  • differences in class inclusion, transect filtering, or log-range handling,
  • differences in acoustic-to-trawl assignment logic,
  • differences in how bottom-trawl strata are merged and weighted,
  • differences between Sam’s end-to-end survey computations and Macebase Analysis.

From a project-management standpoint, discovering the source of those discrepancies is more valuable than accelerating toward RTMB. If point-estimate parity is not achieved first, a new implementation will only make the disagreement harder to localize.

What Is Portable

Several components are straightforward candidates for plain R reimplementation, and most do not need RTMB at all.

Preprocessing and survey construction

Grid creation, geometry handling, coordinate projection, and file normalization in src/preprocess_survey_data.jl can be ported to R with sf, dplyr, and related tooling.

Support models

TS functions, selectivity curves, age-length lookup logic, length-weight regression, calibration, and near-bottom coefficients are all local computations with limited external dependencies.

Analysis orchestration

The survey-specific scripts in analyses/ encode business rules such as log ranges, classes to keep, and transect filtering. Those belong in R wrappers or configuration files, not in RTMB templates.

What Requires Redesign

The spatial layer is the main blocker for an RTMB conversion.

  • Variogram fitting and conditional simulation: the Julia implementation depends on GeoStats setup and LU-based conditional simulation.
  • Z-distribution selection: the code chooses among several nonnegative families by Monte Carlo histogram comparison and Kullback-Leibler divergence.
  • Conditional field generation: current output is generated by repeated simulation, not by fitting a latent process under a single likelihood.

This means the RTMB question is not “how do we translate src/spatial.jl?” but “what spatial statistical model do we want instead?”

Recommended Path

  1. Freeze existing Julia outputs in analyses/results/ as golden-reference regression targets for any migration work.
  2. Build enough experience running the Julia implementation to document every place where its survey computations can diverge from Macebase Analysis.
  3. Create a reconciliation plan focused on point estimates: run deterministic, uncertainty-off cases and compare every intermediate product against standard survey outputs.
  4. Move the survey-result computation inside each simulation round to Macebase Analysis wherever feasible, so the uncertainty process becomes a wrapper around the standard survey engine instead of a parallel survey implementation.
  5. Only after that, decide whether the uncertainty-generation layer should remain in Julia, be ported to plain R, or be partially redesigned.
  6. Consider RTMB only if the team later decides to replace the current spatial bootstrap with a fitted latent-variable model. That would be a methodological change, not a maintenance-oriented port.
Recommended sequencing: reconcile point estimates first, integrate with Macebase Analysis second, choose the implementation language third, and consider RTMB only as a later modeling option.

Evidence

The conclusions above are based on repository structure and code inspection.

  • README.md describes the project as Julia software and points users to Julia-based workflows.
  • src/ATBootstrap.jl contains the main bootstrap loop and per-iteration stochastic logic.
  • src/types.jl shows that ScalingClassProblem is built around spatial simulation setup.
  • src/spatial.jl contains the GeoStats-based spatial machinery and the Monte Carlo z-family selection.
  • R/funs.R and R/ATBootstrap.R still contain placeholders for the core spatial layer, which means the R port is not yet a trustworthy foundation for RTMB work.
  • The project notebook and manuscript materials indicate the method was intended to follow the standard MACE survey workflow closely, which makes the current point-estimate disagreement especially important to resolve before any reimplementation effort.

Runtime check during review: Julia 1.11.7 and R 4.5.2 were available locally. The assessment was structural; the full analysis pipeline was not executed as part of this report.
